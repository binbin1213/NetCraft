# NetCraft 洞察

Route: C
基于 6 个维度 + 文件分析 + 交叉验证

## 一句话判断

这是一个**真实可用、超出原型水准的前端**，挂着一个**还没长成型的后端**，外面套着一层**比代码跑得更快的文档**。它能跑、能演示、能给自己用；但它现在不适合给第二个人用，也不适合按 README 说的方式部署。

## 洞察 1：项目真正的分界线不在「前端/后端」，而在「谁的代码有验证」

把 4,800 行代码按「是否被实际执行验证过」切一刀：

| 层 | 行数 | 验证状态 |
|---|---|---|
| 前端 | 3,617 | 构建通过、lint 有 29 个 error、浏览器实测可交互 |
| 后端 | 488 | **从未运行**（依赖装不上），全部结论来自阅读 |
| 测试 | 516 | 3/4 无法导入、1/4 自测副本 |

这意味着：前端的问题是「已知的、可修的」，后端的问题是「未知的、可能更多」。任何人接手这个项目，第一件该做的事不是加功能，而是**让后端跑起来**——现在的 488 行代码是一份「阅读过的代码」，不是「验证过的服务」。

## 洞察 2：文档不是滞后，是「比代码早一步」

通常技术项目的问题是文档更新不及时。这里更特殊：`审查报告.md` 描述的是**一次没有提交的修改**，`可观测性增强建议.md` 描述的是**一份没有实施的建议**，`测试清单.md` 测试的是**一组不存在的路由**。三份文档都在 git 的同一个提交里（`9ccff4d feat: add password validation tests and Chinese documentation`）。

再看提交信息：「add password validation tests」——确实加了 4 个测试文件，但被测函数不存在。**提交信息、文档、代码三者描述的是三个不同的项目状态。**

这不是粗心，而是一种可识别的模式：先写「目标状态」，再写代码，最后忘了回头对齐。它的危害在于**误导下一个读者**——包括下一个 AI 助手。如果有人问「这个项目的 JWT 安全吗」，读 `审查报告.md` 会得到「已修复」的答案，读代码会得到「有硬编码默认值」的答案。

## 洞察 3：前端作者和后端作者像是两个人

对比两端的代码风格：

| 维度 | 前端 | 后端 |
|---|---|---|
| 类型 | `strict: true`、`DeviceType` 联合类型、泛型 `Node<DeviceData>` | 无类型标注（`def get_password_hash(password)`） |
| 分层 | 组件 / store / utils / api / i18n / types 六层 | 全部塞在 `main.py` |
| 注释 | 有设计意图说明（autoLayout 的 handle 分配逻辑） | 几乎无 |
| 错误处理 | ErrorBoundary + 401 自动登出 | `except Exception as e: yield f"Exception: {str(e)}"` |
| 依赖管理 | 版本固定（`^` 语义化） | 12 个依赖 0 个固定版本 |

前端的 `autoLayout.ts` 里有这样的注释：「3 ports, 1 edge -> offset = floor((3-1)/2) = 1」，作者在思考几何问题。后端的 `ai_service.py` 里，`dashscope.api_key` 直接当全局变量改写，没有考虑并发。

**推论**：这不是团队协作的产物，更像是「一个人擅长前端，后端是顺手写的」。因此改进策略应该不同——前端做增量优化，后端做**重写而非修补**。488 行不值得逐行修，值得按正确的分层重写一遍。

## 洞察 4：最有价值的资产是那个 19KB 的知识库，而它被浪费了

`RAG/KnowledgeBase/` 5 篇文档、11,957 字符，覆盖家庭网络架构、OpenWrt 基础、OpenClash、AdGuard Home、稳定性优化。内容具体到「AdGuard Home 占 53 端口、Dnsmasq 退到 5353」这种可执行细节。

但它现在的作用只是「塞进 prompt 让模型参考」，没有结构化、没有被验证、没有版本管理。而这批内容恰恰是这个项目最难被复制的部分——画布 UI 谁都能写，把 OpenClash 和 AdGuard 的端口冲突讲清楚需要真实踩坑经验。

**如果只能给一条建议**：把知识库从「prompt 附件」升级为「产品资产」——结构化字段（设备/服务/端口/依赖关系）、可校验、可在 UI 上直接生成对应节点和连线。这样 AI 助手从「聊天窗口」变成「知识驱动的配置生成器」，画的图直接来自知识库，而不是模型幻觉。

## 洞察 5：安全问题的权重被误判了

按「修起来多贵」排序，而不是按「听起来多严重」：

| 问题 | 听起来 | 实际风险 | 修复成本 |
|---|---|---|---|
| SECRET_KEY 有默认值 | 严重 | **高**（可伪造任意用户） | 3 行 |
| `/api/chat` 无鉴权 | 中 | **高**（盗刷 API 额度 + SSRF） | 1 行 |
| `dashscope.api_key` 全局串号 | 隐蔽 | **高**（多用户时 A 用 B 的 key） | 改成传参 |
| 密码无复杂度校验 | 中 | 低（自部署场景） | 需先写函数 |
| JWT 15 分钟过期 | 低 | 低（体验问题，不是安全问题） | 3 行 |
| db 口令硬编码 | 严重 | 低（内网 compose） | 改 env |

前三个修复成本加起来不到 20 行，但都属于「一旦多用户部署就立刻出问题」的类型。而项目里反复出现的文档问题（审查报告说已修）恰好掩盖了这三个。

## 洞察 6：这个项目的「完成度」被两种错觉同时高估和低估

- **被高估**：文档说已完成的安全修复、云端自动保存、完美 i18n，实际都没有。
- **被低估**：`PROJECT_STATUS.md` 列为「待开发」的图片导出、后端持久化、模板系统，实际都做完了。

结果是一个奇怪的错配：**该做的事被记成做完了，做完的事被记成还没做。** 这种情况通常是「文档写在开发之前」+「开发完不回填」的组合。修复方法很朴素：把 5 份文档合并成 1 份，且只写「代码里能用 grep 验证」的内容。

## 如果要继续做，优先级排序

**P0（不修就不能给别人用）**
1. `/api/chat` 加 `Depends(get_current_user)`；`dashscope.api_key` 改为按请求传参。
2. `SECRET_KEY` 去掉默认值，缺失即启动失败；两份 compose 补传 `SECRET_KEY`。
3. 修 `backend/Dockerfile` 的 COPY 路径（或把 compose 的 context 改成 `.`）。

**P1（结构性债务）**
4. 合并两套项目系统：本地项目迁到云端，或明确「未登录=本地、登录=云端」并做同步。
5. 前端补 `auto_layout` 动作分支；AI 加边时复用 `onConnect` 的去重逻辑。
6. 删掉 4 份跑不起来的测试，或先实现 `validate_password` 再让它们跑。

**P2（质量）**
7. 后端拆层：`api/` + `services/` + `repositories/`，`main.py` 只留路由注册。
8. 引入 Alembic；`echo=True` 改由环境变量控制。
9. i18n 补齐 AiAssistant / Login / Canvas 的硬编码文案。
10. 修 `Controls` 配色；`temporal` 加 `limit`；`dagreGraph` 改为函数内创建。

**P3（产品）**
11. 把知识库结构化，让 AI 生成的拓扑可追溯到具体文档条目。
12. 补 JSON 导入（现在只能导出，是单向的）。
13. 实现环路/IP 冲突/瓶颈检测——这是 `PROJECT_STATUS.md` 里唯一「说没做也确实没做」的功能，也是这个产品区别于普通画图工具的核心。

## 最后一句

这个项目最值得肯定的不是它的 UI（虽然 UI 确实是全项目最好的部分），而是**作者对自己要做什么很清楚**：设备类型、连线介质、向导规则、知识库主题，全部指向「家庭实验室网络设计」这个具体场景，没有滑向通用画图工具。这个定位的清晰度，比代码质量更难得。
